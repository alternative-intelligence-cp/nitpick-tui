# 0.0.0 — the language probes — PLANNED (the execution record is appended as steps land)

> **Scope:** fourteen small Nitpick programs that ask the compiler whether the
> shapes `meta/specs/` depends on are spellable, compilable and correct. No
> library code is written in this subcycle. What it produces is **a verdict per
> probe** and, where a verdict is negative, an amended specification and a
> recorded decision.
>
> **Why first.** `meta/specs/` was written against the language's
> documentation, and the compiler project's own most expensive finding is that
> *a construct that parses is not a construct that works* — most of its cycle
> 0.4 was repair, and every repair dated to the cycle that had parsed the
> construct. Several of this library's load-bearing shapes have never been
> exercised in the combination it needs. T-056 already exists because one of
> them (a struct holding a borrow) is expected to be interesting; the rest are
> unknown until asked.

---

## 1. Where you are

- Nothing is built. `src/` holds empty directories.
- The compiler is at `../../nitpick`, cycle 1.5 (verification), self-hosting
  declared under D-202. **Do not build it from here and do not read its `build/`**: the
  artifact these probes use is the pinned toolchain the board names
  (`../BOARD.md`, W-18) — `$NPKC` and `$NPKRT`, supplied by the orchestrator or
  set by hand from `../.internal/toolchain/<commit>/`.
- There is no `ntui` harness yet. **Probes are run by hand**, one command each,
  and that is deliberate: the harness is 0.0.2 and building it against an
  unverified set of language assumptions is the mistake this subcycle exists to
  avoid.
- The probes live in `tests/probe/` and **stay in the tree permanently**. They
  are a regression suite for the language shapes this library depends on, and
  the harness picks them up at 0.0.2 as ordinary `program`-stage entries.

---

## 2. The command

For each probe, from the `ntui` tree root, with `$NPKC` and `$NPKRT` from the pinned
toolchain (the board names the commit, W-18):

```
$NPKC tests/probe/probeNN_name.npk -o /tmp/p.ll \
  && llc -O0 -filetype=obj -relocation-model=static /tmp/p.ll -o /tmp/p.o \
  && ld.lld -static /tmp/p.o $NPKRT -o /tmp/p \
  && /tmp/p ; echo "exit $?"
```

A probe that is **expected to be refused** stops at the first command, and its
verdict is the diagnostic code and span, recorded verbatim.

**Every probe exits 0 on success and a distinct positive code per assertion it
fails**, in the compiler's own house style, so a failure names itself.
`exit 0` additionally asserts, through D-151 and D-188, that nothing leaked.

## 3. Decisions taken at planning

- **P-0 — a probe's filename may not begin with a digit**, so probes are named
  `probeNN_topic.npk` and the `mod:` line matches. A file's module name must
  equal its basename, and no identifier may begin with a decimal digit — D-147
  gives that opening to numeric literals alone, so `mod:01_argv;` is refused
  `NITPICK-LEX-003` with `NITPICK-RESOLVE-005` behind it. *Measured the hard
  way in `nitpick-posix`'s probe 02, 2026-09-03, after every plan in the
  ecosystem had written `01_name.npk`.*
- **P-1 — a probe is a program, never a library file.** It has its own `main`
  and `failsafe` and imports nothing from `src/`. A probe that needed library
  code would be testing the library, which is what every other cycle is for.
- **P-2 — a refused probe is a *result*, not a failure of the subcycle.** Two
  probes (02, and possibly 08) are expected to be refused, and their value is
  the exact diagnostic. The subcycle fails only if a probe's verdict is
  *undecided* — a crash in the compiler, a hang, or an output nobody can read.
- **P-3 — the verdict is recorded before the next probe is written.** A batch
  of fourteen written and then run together is a batch where the third one's
  answer would have changed the fourth one's design.
- **P-4 — a negative verdict amends `meta/specs/` in the same commit.** Not a
  note to self, not a TODO. The specification is the authority (T-002) and an
  authority that is known to be wrong and not corrected is worse than none.
- **P-5 — the probe programs stay.** They become `tests/probe/`'s permanent
  suite, so a compiler change that breaks one of these shapes is caught by
  `ntui`'s own harness rather than by a widget failing mysteriously in 0.12.

## 4. The probes

Each entry: **what it asks**, **the shape**, **why it matters**, and **what a
negative verdict costs**.

### 01 — a struct holding a borrow, built by literal, passed down

**Asks:** can `Surface { Buffer->:buf; Rect:area; }` be constructed by struct
literal and passed down two call levels?

```nitpick
struct:Bufr = { Vec<int32>:cells; uint16:w; uint16:h; };
struct:Surf = { Bufr->:buf; uint16:x; uint16:y; uint16:w; uint16:h; };

func:inner = NIL(Surf:s, uint16:col, int32:v) never fails {
    if (col >= s.w) { pass NIL; }
    s.buf.cells.items[(s.y => int64) * (s.buf.w => int64) + ((s.x + col) => int64)] = v;
    pass NIL;
};
func:outer = NIL(Surf:s) never fails {
    Surf:child = Surf{ buf: s.buf, x: s.x + 1u16, y: s.y, w: s.w - 1u16, h: s.h };
    drop inner(child, 0u16, 42i32);
    pass NIL;
};
```

**Matters because** the entire drawing API is this shape
(`specs/SCREEN_MODEL.md` §9, `specs/WIDGET_MODEL.md` §1). Sub-surfaces are
built by literal from a parameter's field, never returned from a function
(T-056).

**A negative verdict costs** the `Surface` type: the drawing API becomes
`(Buffer->:buf, Rect:area)` as two parameters, clipping becomes a helper that
takes both, and `specs/SCREEN_MODEL.md` §9 and `specs/WIDGET_MODEL.md` §2 are
rewritten. Workable, uglier, and much better known now.

### 02 — the same struct, returned — **expected refused**

```nitpick
func:sub = Surf(Surf:s, uint16:dx) never fails {
    pass Surf{ buf: s.buf, x: s.x + dx, y: s.y, w: s.w - dx, h: s.h };   // expected: refused
};
```

**Asks:** does the escape analysis refuse a returned value carrying a borrow
that arrived as a parameter?

**Matters because** T-056 asserts it does, and the whole "build by literal at
the call site" convention exists because of it. **If this is *accepted*,** T-056
is over-cautious and `surface_sub()` can exist — which is a nicer API, and the
specification gains a function.

**Record the diagnostic code and span verbatim either way.**

### 03 — a large array of 32-byte POD values

**Asks:** does a `Vec<T>` of 12 000 32-byte structs fill, read, copy and clear
without trapping, and what does it cost?

```nitpick
struct:Cell32 = { uint8[14]:text; uint8:len; uint8:flags; uint32:a; uint32:b; uint32:c; uint32:d; };
```

**Matters because** `Cell` is exactly this (T-050) and a screen buffer is
exactly this array. Also measures: `#size_of<Cell32>()` — **assert it is 32**,
because a padding surprise changes the memory budget and the spec's number.

**A negative verdict costs** the cell layout, and `specs/SCREEN_MODEL.md` §2's
table is re-derived from what the compiler actually lays out.

### 04 — a tagged enum with payloads, in a `pick` and in an array

```nitpick
enum:Code = { Ch(char32); Fn(uint8); Plain; Other(uint32); };
```

**Asks:** destructuring in a `pick`, storing in a `Vec<Code>`, comparing,
`#[derive(Eq, Debug)]`, and `#size_of<Code>()`.

**Matters because** `KeyCode`, `Constraint`, `Event` and `Color`'s kind are all
this shape, and `Event` in particular lives in a fixed-capacity ring.

**A negative verdict costs** the event vocabulary: parallel-field structs
instead of payload variants, which is a worse API and a bigger `Event`.

### 05 — `move T:v` into a generic container

**Asks:** does `list_push`-shaped code work for `T = int32` and for `T` an
owning struct (one holding a `string`), including the drop of the container?

**Matters because** `Vec<T>` (T-006) must hold both, and `Text` /
`Vec<Line>` hold owning values.

### 06 — an inherent impl on a generic struct with a mutating pointer receiver

```nitpick
impl:<T>:Vec<T> = {
    func:push2 = NIL(Vec<T>->:self, move T:v) never fails { … };
};
```

**Asks:** does D-171's inherent family impl work, called as `v.push2(x)`?

**Matters because** the widget builder chain (`specs/WIDGET_MODEL.md` §2) and
every container method depend on it. **Also asks the free-function form**, so
the fallback is measured in the same probe.

### 07 — a trait with a `Self->` receiver through a generic bound

```nitpick
trait:Draw = { func:render = NIL(Self->:self, Bufr->:buf, uint16:x, uint16:y); };
func:draw_it<W: Draw> = NIL(W->:w, Bufr->:buf) never fails { drop w.render(buf, 0u16, 0u16); };
```

**Asks:** two impls, dispatched statically through the bound; and separately
through `dyn Draw`.

**Matters because** this is the `Widget` trait exactly
(`specs/WIDGET_MODEL.md` W-2).

### 08 — an `async` trait method through a bound and through `dyn`

**Asks:** `async func:update = NIL(Self->:self, …)` on a trait, driven by
`await` through a generic bound, and — separately — through `dyn`.

**Matters because** `Program.update` is this (`specs/EVENT_MODEL.md` §2).
Object safety admits `async` with a `Self->` receiver since D-185/1.1.12d, so
both should work; **the `dyn` half is the one to watch**, since it needs the
frame-size tail.

**A negative verdict on the `dyn` half costs nothing** — `run<P: Program>` is
generic and static dispatch is the intended path. Record it as a constraint on
future multi-screen composition (O-E2).

### 09 — a kernel structure in a `buffer`, through `ioctl`

```nitpick
buffer:t = buffer_new(36i64);
Result<int64>:r = sys(16i64, tty_fd, 21505i64, t.ptr);      // TCGETS = 0x5401
uint32:iflag = <-(#ptr_add<uint32>(t.ptr, 0i64));
```

**Asks:** `buffer_new`, `#ptr_add<T>` typed access, a pointer argument to `sys`
(the `ptrtoint` at the trampoline), and reading back four `uint32`s and 19
bytes at the documented offsets. **Asserts the structure is 36 bytes** by
writing a sentinel past it in a 64-byte buffer and confirming `TCSETS` +
`TCGETS` round-trips without touching it.

**Matters because** every device call is this shape
(`specs/TERMINAL_MODEL.md` §3), and the 36-vs-60 byte question is the single
most likely place to be wrong about the kernel.

**Needs a terminal.** Run it under one; if unavailable, `open("/dev/null")`
and assert `ENOTTY` instead, which still exercises everything but the
round trip.

### 10 — `eventfd2`, `io_watch`, and one `suspend_io` over two descriptors

**Asks:** create an eventfd (`syscall 290`, flags `EFD_CLOEXEC | EFD_NONBLOCK`
= `524288 | 2048`), arm it and a pipe read end with `io_watch`, park once with
`suspend_io`, have another task write to one of them, and confirm the park
returns and the right descriptor is readable.

**Matters because** the runtime's single multi-descriptor wait is this exactly
(`specs/EVENT_MODEL.md` E-5, T-072), and it is the mechanism that replaces the
`select` the language does not have.

**A negative verdict costs** the post channel's design and possibly the loop's:
the fallback is a short-deadline `suspend_io` on the terminal alone plus a
polled queue, which is worse and would want recording as a decision.

### 11 — `rt_sigprocmask` and `signalfd4`

**Asks:** build an 8-byte sigset with bit 27 set (`SIGWINCH` = 28),
`rt_sigprocmask(SIG_BLOCK=0, set, NULL, 8)` (syscall 14),
`signalfd4(-1, set, 8, SFD_CLOEXEC|SFD_NONBLOCK)` (syscall 289), send
`SIGWINCH` to self (`kill`, syscall 62, with `getpid`, syscall 39), read the
128-byte record and assert `ssi_signo == 28`.

**Matters because** T-011 puts every signal on this path and the language has
no other. It is also the probe most likely to reveal an ABI detail the plan has
wrong — the sigset size in particular.

### 12 — module state with an atomic interior, written from `failsafe`

**Asks:** a module-level `fixed` binding holding a struct with an
`atomic<int32>` and a fixed-size byte array; written from ordinary code;
**read and written from `failsafe`** after a deliberate trap.

**Matters because** the restore record is this exactly (T-012), and "can
`failsafe` read module state at all" is the assumption the library's headline
safety property rests on. D-211 makes module state `fixed`, so the mutable
interior has to be reached through something — this probe finds out through
what.

**A negative verdict is the most expensive one in the set.** The fallback would
be the runtime-registry mechanism the language uses for its own three
registries, which `ntui` cannot reach from library code; the next fallback is a
request to the compiler, and the design blocks on it. **Run this probe early.**

### 13 — a trap reaches `failsafe`, and `failsafe` can write to a descriptor

**Asks:** open a file, write a marker, trap deliberately (an out-of-bounds
index), and in `failsafe` write a second marker to that descriptor and exit
non-zero. Assert both markers are in the file.

**Matters because** it is the whole restore contract (`specs/SAFETY.md` §2) in
one program: `defer` does not run, `failsafe` does, and it can perform I/O.

### 14 — `string_bytes` / `string_from_bytes` at the borrow edges

**Asks:** `string_bytes(s)` into a function that decodes it, the slice's `.len`
and `.ptr`, a `string_from_bytes` view built in `wild` context, and the four
edges the escape analysis governs: passing the slice down (legal), returning it
(refused), storing it in a struct that outlives the call (refused), holding it
across an `await` (refused).

**Matters because** the whole text layer takes `uint8[]` and every widget hands
one down, and D-186 made `string_slice` an owned copy for exactly the
use-after-free this probe maps.

## 5. The steps

Each step is one commit.

**Step 1 — the risky four, first: 12, 09, 11, 10.** These are the probes whose
negative verdicts change the *architecture* rather than an API. Run them, record
verdicts, and if any is negative, **stop and re-plan** before writing another
probe. The order within the four is by cost of being wrong: 12 (the restore
record) is the most expensive.

**Step 2 — the language-shape probes: 01, 02, 03, 04.** These decide the cell
and event representations and the drawing API.

**Step 3 — the dispatch probes: 05, 06, 07, 08.**

**Step 4 — the remainder: 13, 14.**

**Step 5 — the record and the amendments.** Every verdict written into §7
below; every consequence written into `meta/specs/` and `meta/DECISIONS.md`;
`tests/probe/README.md` written, saying what the directory is for and that a
probe is never deleted.

## 6. What the executor should know

- **The reserved words will bite immediately.** `buffer`, `raw`, `move`, `in`,
  `end`, `limit`, `any`, `fd`, `error`, `on` — `specs/BUILD.md` §7 is the list.
  A probe about `ioctl` wants a local called `buffer` and a probe about signals
  wants one called `fd`; neither is available.
- **`discard(x);` takes parentheses. `defer { … }` takes no trailing
  semicolon.** Declarations end `};`; control-flow blocks do not.
- **Adjacent string literals do not concatenate.**
- **A file's `mod:` name must equal its basename**, or the loader reports
  `NITPICK-RESOLVE-005` at line 1 and says nothing about the name.
- **`raw` is licensed only on a `never fails` callee** (D-163). An `async`
  callee is never `never fails`, so `raw await f()` is unspellable; use
  `relay await`, `await … ?| d`, or `await … ?! E`.
- **Strings are move-only** (TYPE-046). Build a name per use rather than
  holding one binding across lines.
- **A `failsafe` must name every reachable error** (REACH-002), including the
  system ones the program's own machinery can raise. Copy the arm set from
  `../../nitpick/tests/backend/programs/proc_tool.npk` and prune.
- **Exit 0 means "and nothing leaked"** (D-151, D-188). Every probe exits 0 on
  success on purpose.
- **`llc` and `ld.lld` must be the pinned 20.1.2.** `llvm-config --version`.
